# Mobile Refresh, Demo Seed and k6 Scenarios Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement and independently review each task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Keep loaded mobile screens stable across tab switches, seed repeatable synthetic demo machines, and use k6 to send telemetry through the deployed API for healthy, alert, recovery, and unknown-state scenarios.

**Architecture:** Keep focus refreshes but preserve the last successful query result while new data loads. Seed demo entities through the real auth, machine, baseline, provisioning and claim workflows, temporarily assigning the existing provisioning role to an isolated demo owner. Store generated demo credentials and device keys only in an ignored VPS file. k6 reads those fixtures and sends the API's implemented machine-scoped telemetry route over HTTPS.

**Tech Stack:** Expo SDK 58, React Native Testing Library 14, Go API routes, PostgreSQL, ClickHouse through the API-owned outbox, k6 `grafana/k6:1.8.2`.

**Spec:** `docs/superpowers/specs/2026-11-25-demo-seed-k6-design.md`

## Global Constraints

- Keep refetch-on-focus behavior for freshness, but retain loaded content while the refresh is pending.
- Existing production accounts and machines must remain unchanged. Seed a separate demo owner and label all seeded machines as demo data.
- Seed the current API routes and domain rules; do not write fake telemetry directly to PostgreSQL or ClickHouse.
- Revoke the temporary `device_provisioner` role after provisioning, including failure cleanup.
- Raw demo passwords, device API keys and claim codes must stay in ignored `deploy/secrets/k6-demo-fixtures.json`, mode `0600`, and never appear in logs or committed files.
- Use one independently seeded machine/device pair per k6 VU and scenario to avoid out-of-order events and detector state sharing.
- Synthetic RMS values demonstrate API/detector behavior only; they do not model physical sensor output or calibrate a real machine.
- Keep the current implemented telemetry route `POST /v1/machines/{machine_id}/telemetry`; device-scoped `POST /v1/devices/me/telemetry` remains a separate feature.
- Preserve existing auth, authorization, no-store, telemetry timestamp and outbox behavior.

## Review Focus

1. A focus refresh must not hide previously loaded machine, alert or history data; Task 13 regression tests exercise this.
2. Seed failure must not retain a provisioning role or leave a partially usable credentials file; Task 14 failure cleanup and tests exercise this.
3. The seed output must not contain incomplete or cross-wired device/machine fixtures; Task 14 tests validate each scenario pair.
4. K6 event IDs and timestamps must satisfy ingestion rules under repeated simulations; Task 15 tests validate unique IDs and monotonically increasing timestamps per device.
5. Alert checks must match the current configured thresholds and sustained counts; Task 15 exercises healthy/no-alert, sustained anomaly, recovery, and unknown-state behavior.

### Task 14: Seed isolated synthetic demo data

**Files:**
- Create: `deploy/scripts/seed-demo-data.py` and `deploy/scripts/test-seed-demo.py`.
- Modify: `deploy/README.md` and `.github/workflows/ci.yml`.

**Interfaces:**
- The seed defaults to owner email `demo@machine-whisperer.test`, accepts `DEMO_OWNER_EMAIL` as an override, and generates a 32-character random password. It writes owner credentials plus fixture arrays to `deploy/secrets/k6-demo-fixtures.json` with mode `0600`; it refuses to overwrite an existing fixture file.
- The fixture JSON has `api_base_url`, `owner_email`, `owner_password`, `simulations`, and `scenarios`. Each of the four scenario arrays has exactly `simulations` entries containing `machine_id`, `machine_name`, `device_id`, `device_api_key` (`device_id.secret`), `mean_rms_g`, and `stddev_rms_g`.
- For each of `healthy`, `alert`, `recovery`, and `unknown`, create `SIMULATIONS` machines and claimed software devices. `SIMULATIONS` defaults to `1` and is capped at `3` to stay within the per-IP enrollment budget. Machine names start with `Demo <scenario>`. Use synthetic baseline mean `0.04 g`, standard deviation `0.005 g`.
- Use `POST /v1/auth/signup`, login, `POST /v1/machines`, `PUT /v1/machines/{id}/baseline`, the authenticated device provisioning flow, and `POST /v1/devices/claim`. Temporarily insert the demo owner in `user_roles` for provisioning, then revoke the role. The existing live owner and machines are never used or modified.
- The seed tool uses the public API for owner routes and a trusted local Docker execution of the API container for the restricted provisioning route. It removes the new owner, associated entities and partial fixture output if any step fails.
- Tests use an isolated fake HTTP/Docker boundary for seed orchestration; existing API integration tests continue to cover real PostgreSQL constraints and enrollment with Testcontainers.

### Task 15: Add k6 telemetry scenarios

**Files:**
- Create: `deploy/k6/telemetry-scenarios.js` and `deploy/scripts/run-k6-demo.sh`.
- Create: `deploy/scripts/test-k6-demo.sh`.
- Modify: `.github/workflows/ci.yml` and `deploy/README.md`.

**Interfaces:**
- `SCENARIO` selects `healthy`, `alert`, `recovery`, `unknown`, or `all`; `SIMULATIONS` selects the number of independent fixtures per scenario.
- Each VU uses its own fixture and sends events to `POST /v1/machines/{machine_id}/telemetry` with a unique UUID, increasing UTC timestamps, and the fixture's device bearer key.
- `healthy` sends RMS values near the baseline and verifies no alert; `alert` sends three running values with z-score at least 3 and verifies an active alert; `recovery` opens then recovers an alert with three values at or below z-score 2; `unknown` sends high RMS with unknown state and verifies no alert.
- Use `mean + 0.5*stddev` for healthy values, `mean + 4*stddev` for sustained alert values, and the exact baseline mean for recovery values. All event timestamps increase by one second per machine and all event IDs are UUIDs.
- The script verifies HTTP 202, alert state, and eventual history visibility through the API/outbox. It never writes directly to either database.
- `run-k6-demo.sh` runs the pinned public image `grafana/k6:1.8.2` with a read-only mount of the ignored fixture file and no application secret values in command output.

- All seed credentials and device keys stay on the VPS outside GitHub Actions and the repository.
