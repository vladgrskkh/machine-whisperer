# Signup Implementation Plan

> **For agentic workers:** Use superpowers:executing-plans or
> superpowers:subagent-driven-development to implement task by task.

**Goal:** Add persistent user accounts and `POST /v1/auth/signup` as one small PR.

**Architecture:** A handler delegates validation and account creation to an auth
use case. Infrastructure supplies Argon2id hashing and a pgx repository; domain
contains the user model and validation rules. Application wiring stays outside
domain and use case packages.

**Tech stack:** Go, chi, pgx, Goose, Argon2id, testify and real HTTP transport.

**Spec:** `docs/superpowers/specs/2026-11-10-user-auth-design.md`, relative to `api/`.

## Global constraints

- Follow `AGENTS.md`; this plan implements only the signup slice of auth.
- No organizations, email verification or password reset; login is a later PR.
- Signup returns `id`, `email`, `created_at` with `201`; no tokens or password hash.
- Trim and lowercase email; unique canonical email, maximum 254 bytes, no
  display-name syntax or provider-specific rewriting.
- Password: 15–128 Unicode characters, maximum 512 bytes; preserve it exactly.
- Argon2id: 19 MiB memory, two iterations, one lane and a fresh random salt.
- Reject unknown JSON fields, malformed bodies and bodies over 8 KiB with `400`.
- Error envelope: `{"error":{"code":"...","message":"..."}}`.
- Duplicate signup returns `409`; rate limiting returns `429`; internal failures
  return `500` without exposing their cause.

## Review focus

- Concurrent registration of the same canonical email creates exactly one user.
- Unicode password boundaries and whitespace are handled without alteration.
- An invalid request never creates an account or invokes expensive hashing.
- Database errors never reveal SQL, connection strings or password material.
- Rate limits use a trustworthy client address and run before password hashing.

## Task 1: Account creation through real dependencies

**Files:**

- `internal/domain/user/user.go`, `user_test.go`: user fields and validation.
- `internal/usecase/auth/signup.go`: signup orchestration and consumer interfaces.
- `internal/infrastructure/auth/password/argon2id.go`, `argon2id_test.go`:
  salted PHC-format hashes; 16-byte salt and 32-byte output.
- `internal/infrastructure/user/postgres/repository.go`: parameterized insertion
  and mapping the email uniqueness violation to a domain sentinel error.
- `migrations/202611100001_create_users.sql`: users with UUID primary key,
  canonical email uniqueness, password hash and UTC creation timestamp.
- `internal/application/signup_integration_test.go`: real HTTP and PostgreSQL.
- `internal/testutil/postgres.go`: isolated test schema, migrations and cleanup.

**Interfaces:** `Signup(ctx context.Context, email, password string)
(user.User, error)` on the auth use case. Define repository and password-hasher
interfaces in `usecase/auth`; implementations live in infrastructure.

- [ ] Add pinned pgx, Goose and password-hashing dependencies. Introduce a
  Testcontainers PostgreSQL integration harness with a separate schema per test
  suite and guaranteed cleanup. A missing Docker runtime must produce a clear
  failure for integration runs, not a silent skip.
- [ ] Write validation tests for invalid email, display-name email syntax,
  canonicalization, password lengths 14/15/128/129, byte limit and Unicode.
  Watch them fail, implement the domain rules and rerun.
- [ ] Write password tests proving the hash verifies the exact original input,
  rejects a changed password and differs between two hashes of the same input.
  Watch them fail, implement hashing and rerun. Keep verification reusable for
  the later login feature.
- [ ] Write a failing account-creation integration test: signup creates one row
  with canonical email and a verifiable password hash. Implement the migration,
  repository and use case; rerun to green.
- [ ] Add concurrent duplicate-signup tests: exactly one creation succeeds,
  other attempts map to the duplicate sentinel and no extra row is stored.
  Verify database constraints enforce this behavior.

## Task 2: HTTP endpoint, wiring and checks

**Files:** `internal/handler/auth/signup.go`, `internal/handler/auth/dto.go`,
`internal/handler/middleware/rate_limit.go`, `internal/application/application.go`,
`internal/application/signup_integration_test.go`, `cmd/api/main.go`, `Makefile`,
`README.md`, `.github/workflows/ci.yml` at the repository root.

**Interfaces:** `POST /v1/auth/signup` consumes email/password JSON and delegates
to Task 1's use case. Wire configuration, the database pool and handler in the
application layer. Keep the current server lifecycle behavior intact.

- [ ] Write failing real-transport tests with `httptest.NewServer`: successful
  signup returns only public user fields, duplicates return `409`, validation
  returns `400`, and errors use stable codes. Implement the handler and wiring.
- [ ] Cover trailing JSON, unknown fields, malformed/oversized bodies, and
  database failure returning `500` without internals. Implement bounded decoding
  and error mapping; rerun the tests.
- [ ] Write rate-limit tests using a controlled clock: 30 attempts per minute
  per client IP, then `429`; requests work after the window resets. Forwarded
  headers must be ignored unless the peer is a configured trusted proxy.
  Implement a bounded single-instance limiter before expensive work. Login
  failure limits belong to the later login plan.
- [ ] Add service migration commands and an integration-test target. Document
  database setup and test configuration. Extend CI with PostgreSQL and the
  integration command; retain the existing build and lint jobs.
- [ ] Run formatting, build, unit tests, integration tests, race detection and
  lint. Request a fresh code review; address important findings. Commit with
